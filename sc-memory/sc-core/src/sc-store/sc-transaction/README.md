
Транзакционная модель sc‑памяти
==============================

Этот модуль добавляет к sc‑машине транзакционную модель: можно сгруппировать набор изменений sc‑графа в одну транзакцию, проверить конфликты и применить либо всё сразу, либо ничего.

Общая концепция
---------------

Транзакция — это логическая группа операций над sc‑памятью (создание, изменение, удаление элементов, изменение содержимого ссылок), которую система либо фиксирует целиком, либо откатывает целиком. Основные цели:

- **Атомарность**: частичное применение изменений исключено.
- **Изоляция**: параллельные транзакции не ломают данные друг друга.
- **Предсказуемость под нагрузкой**: все изменения сначала буферизуются и валидируются, потом применяются единым шагом.

Транзакция не пишет напрямую в память: операции наполняют буфер, где хранятся все изменения до момента коммита.

Архитектура
-----------

Транзакционная подсистема состоит из нескольких ключевых компонентов.

### Менеджер транзакций

`sc_memory_transaction_manager` отвечает за:

- создание и учёт транзакций (выдача уникальных идентификаторов);
- очередь транзакций и пул рабочих потоков;
- структуру `processed_elements` — набор элементов, которые сейчас обрабатываются какими‑то транзакциями;
- координацию конкурентного доступа и корректное завершение работы.

Основной код (агенты, тесты, приложения) создаёт транзакции и отдаёт их менеджеру на выполнение через `sc_memory_transaction_commit()`.

### Транзакция

`sc_transaction` описывает одну активную транзакцию:

- `transaction_id` — уникальный идентификатор;
- `ctx` — контекст sc‑памяти;
- `transaction_buffer` — буфер всех изменений;
- `elements` — хэш‑таблица с элементами, затронутыми транзакцией (write‑set);
- `state` — состояние транзакции (`PENDING`, `EXECUTED`, `FAILED`, `COMMITTED`);
- `monitor` — примитив синхронизации для работы с транзакцией.

Через API транзакции вызывающий код создаёт узлы, дуги, ссылки, помечает элементы на удаление и меняет контент ссылок. Все эти операции работают через буфер, а не напрямую с хранилищем.

### Буфер транзакции

`sc_transaction_buffer` хранит изменения по типам в четырёх хэш‑таблицах:

- `new_elements` — новые элементы;
- `modified_elements` — изменённые элементы (снапшоты `sc_element_data`);
- `deleted_elements` — элементы, помеченные на удаление;
- `content_changes` — изменения содержимого ссылок (`sc_stream *`).

Ключом во всех таблицах служит адрес элемента, приведённый к целому виду. Это позволяет выполнять:

- вставку;
- поиск по адресу;
- проверку наличия элемента

в среднем за $O(1)$.

Операции вида `*_new / *_change / *_remove / *_content_set` только обновляют соответствующие хэш‑таблицы буфера. Физические изменения структуры графа выполняются позже — при применении транзакции.

### Версионирование

При применении модификаций:

- для каждого изменённого элемента создаётся новая версия (`sc_element_version`);
- версия добавляется в соответствующий сегмент версий (`sc_version_segment`).

Версии используются для хранения истории изменений и потенциального анализа прошлых состояний. Снапшоты `sc_element_data`, накопленные в буфере, играют сразу две роли:

- исходное состояние для валидации (оптимистичный контроль);
- источник данных для формирования новой версии при коммите.

Поток выполнения транзакции
---------------------------

Типичный сценарий использования транзакций выглядит так:

1. Создание транзакции:

```c
sc_transaction *txn = sc_memory_transaction_new(ctx);
```

2. Выполнение операций внутри транзакции:
    - `sc_memory_transaction_node_new`;
    - `sc_memory_transaction_link_new`;
    - `sc_memory_transaction_arc_new`;
    - `sc_memory_transaction_element_free`;
    - `sc_transaction_element_content_set` и т.п.

Все эти функции:
    - модифицируют только буфер (`sc_transaction_buffer`);
    - добавляют адреса элементов в `txn->elements`.
3. Отправка транзакции на выполнение:

```c
sc_result res = sc_memory_transaction_commit(txn);
```

Менеджер ставит транзакцию в очередь на обработку.
4. Поток‑воркер выполняет цикл:
    - забирает транзакцию из очереди;
    - проверяет пересечение `txn->elements` с глобальным `processed_elements`;
    - если конфликта нет — блокирует элементы (заносит их в `processed_elements`);
    - вызывает `sc_transaction_validate(txn)` и затем `sc_transaction_apply(txn)`;
    - по завершении удаляет элементы из `processed_elements` и обновляет состояние транзакции.

Если при проверке пересечений или валидации обнаружена проблема, транзакция помечается как `FAILED` и изменения не применяются.

Оптимизации по памяти
---------------------

Узким местом первой реализации были структуры данных и управление памятью. Основные изменения:

- **Переход от списков к хэш‑таблицам**.
Раньше буфер работал через линейные списки. Любой поиск или проверка пересечений были линейными по числу изменений и плохо масштабировались при больших транзакциях.
Теперь для новых, изменённых, удалённых элементов и контента используются хэш‑таблицы. Это даёт:
    - $O(1)$ вставку и проверку «есть/нет»;
    - упрощённые и ускоренные проверки конфликтов между транзакциями;
    - снижение трудоёмкости с $O(n \cdot k^2)$ до порядка $O(n \cdot k)$ в нагруженных сценариях (n — число транзакций, k — среднее число элементов в буфере).
- **Минимизация лишних копий**.
Для элемента создаётся неограниченное количество изменений, но **ровно один** snapshot его «старого состояния» в рамках транзакции. Повторные изменения этого же элемента не порождают новые вспомогательные структуры.

Планы по дальнейшему улучшению управления памятью:

- реализовать пул памяти для объектов, связанных с изменениями (снапшоты, служебные записи), чтобы:
    - уменьшить количество обращений к глобальному аллокатору;
    - сделать поведение более предсказуемым под нагрузкой;
- добавить возможность реиспользования контейнеров буфера между транзакциями (object pool для `sc_transaction`).

Оптимизация применения изменений
--------------------------------

С учётом новых структур данных можно заметно ускорить фазу применения (`apply`):

- работать напрямую по хэш‑таблицам:
    - **модификации**: проход по `modified_elements`, создание версий и обновление структур;
    - **удаления**: проход по `deleted_elements` и вызов `sc_memory_element_free`;
    - **контент**: последовательное применение `content_changes` без дополнительных поисков;
- минимизировать время жизни блокировок:
    - захватывать мониторы только на время работы с конкретным элементом;
    - по возможности объединять несколько операций по одному элементу в один критический участок.

Дополнительные направления развития:

- батч‑коммиты (групповое применение нескольких транзакций) для улучшения кеш‑локальности и уменьшения накладных расходов на синхронизацию;
- оптимизации «ленивого» обновления вторичных структур там, где допустима небольшая задержка отражения изменений.

Версионирование: текущий статус и развитие
------------------------------------------

Текущая система версионирования:

- хранит историю состояний sc‑элементов через цепочку `sc_element_version`;
- позволяет анализировать прошлые состояния графа;
- используется при применении транзакций для сохранения зафиксированных состояний.

Однако полные копии состояния и глубокая история могут давать заметные накладные расходы. Планы:

- упростить модель версий под реальные сценарии использования:
    - хранить только изменённые поля или компактные диффы вместо полного `sc_element_data`;
    - ограничивать глубину истории (по количеству версий или по времени);
- рассмотреть отдельный «high‑performance» режим без версий (или с сильно урезанным версионированием) для сценариев, где важнее производительность, чем возможность анализировать прошлые состояния.

Публичный API
-------------

### Управление транзакциями

- Создание транзакции:

```c
sc_transaction * sc_memory_transaction_new(sc_memory_context * ctx);
```

- Отправка транзакции на выполнение:

```c
sc_result sc_memory_transaction_commit(sc_transaction * txn);
```


(Планируется добавить явный `sc_memory_transaction_rollback(sc_transaction *txn)`, когда будет реализован полноценный откат.)

### Операции внутри транзакции

- Создание узла:

```c
sc_addr sc_memory_transaction_node_new(
    sc_transaction const * txn,
    sc_type const type);
```

- Создание ссылки:

```c
sc_addr sc_memory_transaction_link_new(
    sc_transaction const * txn);
```

- Создание дуги:

```c
sc_addr sc_memory_transaction_arc_new(
    sc_transaction const * txn,
    sc_type const type,
    sc_addr * const beg_addr,
    sc_addr * const end_addr);
```

- Логическое удаление элемента:

```c
sc_addr sc_memory_transaction_element_free(
    sc_transaction const * txn,
    sc_addr const addr);
```

- Изменение содержимого ссылки:

```c
sc_bool sc_transaction_element_content_set(
    sc_transaction const * txn,
    sc_addr const * addr,
    sc_stream const * content);
```


Все эти функции:

- не трогают реальные структуры в хранилище;
- только обновляют буфер и набор затронутых элементов транзакции.

Планы по развитию API:

- более удобные высокоуровневые обёртки для C++‑агентов (RAII‑классы для транзакций);
- транзакционные API для шаблонов/запросов (создание/изменение целых паттернов внутри транзакции);
- диагностический API:
    - статистика конфликтов;
    - размер буфера;
    - количество версий, созданных транзакцией.

Направления развития
--------------------

Кратко планы на следующие итерации:

- **Память**:
    - внедрение пула памяти для записей об изменениях;
    - переиспользование структур транзакций и их буферов.
- **Применение**:
    - батч‑коммиты;
    - уменьшение времени удержания блокировок;
    - оптимизации доступа к вторичным структурам.
- **Версионирование**:
    - переход на компактное хранение изменений (диффы);
    - конфигурируемая глубина истории;
    - опциональный режим без версий для высоконагруженных сценариев.
- **API**:
    - явный откат транзакций;
    - вспомогательные высокоуровневые функции для агентов и приложений;
    - расширенная диагностика и метрики производительности.
